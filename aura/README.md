# Aura - AWS Optimizer Orchestrator

Aura is a job scheduling and execution system for AWS optimization workloads. It orchestrates the execution of build and solve phases for optimization jobs using Docker containers and provides comprehensive monitoring and logging.

## Features

- **Job Orchestration**: Manages lifecycle of optimization jobs (build → solve)
- **Parallel Execution**: Configurable limits for concurrent build and solve jobs
- **Plugin System**: Pluggable heuristics for job scheduling (FIFO included)
- **Docker Integration**: Runs optimization tasks in isolated containers
- **Monitoring**: CPU and memory usage tracking
- **Event Storage**: JSONL-based event logging for analysis
- **Configuration**: YAML-based configuration with environment variable overrides
- **Automatic Cleanup**: Optional deletion of large model.pb files after solve completion (saves 300-400MB per job)

## Configuration

Configure Aura using the `configs/config.yaml` file organized in logical sections:

```yaml
# Docker configuration
docker:
  optimizer_image: "registry-git.lsd.ufcg.edu.br/pedro.serey/awsome-savings:or-tools"
  families_mount: "/optimizer-files"
  proto_mount: "/optimizer-proto"
  logs_mount: "/optimizer-logs"
  verbose_docker: false
  dry_run: false

# Scheduler configuration  
scheduler:
  default_max_build: 2
  default_max_solve: 1
  default_poll_interval: 0.2
  job_timeout: 3600

# Storage configuration
storage:
  runs_dir: "./orchestrator_runs"
  max_old_runs: 100
  cleanup_model_after_solve: true      # Auto-delete model.pb after solve (saves 300-400MB per job)

# Monitoring configuration
monitoring:
  log_dir: "./monitor_logs"

# Logging configuration
logging:
  level: "INFO"
  format: "%(asctime)s - %(name)s - %(levelname)s - %(message)s"
```

### Environment Variable Overrides

You can override any configuration using environment variables with the `AURA_` prefix. Use double underscores (`__`) for nested values:

```bash
# Simple values
export AURA_LOGGING__LEVEL="DEBUG"

# Nested configuration sections
export AURA_DOCKER__OPTIMIZER_IMAGE="my-custom-image:latest"
export AURA_SCHEDULER__DEFAULT_MAX_BUILD=4
export AURA_STORAGE__RUNS_DIR="/custom/path"
export AURA_STORAGE__CLEANUP_MODEL_AFTER_SOLVE=false
export AURA_MONITORING__LOG_DIR="/custom/monitor/path"
```

## Usage

### Command Line

After installation, run Aura with:

```bash
# Basic usage
aura --demand-root /path/to/family/directories

# Advanced usage
aura --demand-root /path/to/families \
     --plugin fifo \
     --max-build 3 \
     --max-solve 2 \
     --poll-interval 0.5 \
     --config /path/to/custom/config.yaml
```

### Python Module

```bash
# Run as module
python -m aura --demand-root /path/to/families
```

### Programmatic Usage

```python
from aura.config import get_config
from aura.plugins import load_plugin
from aura.core.scheduler import Scheduler

# Load configuration
config = get_config()

# Access configuration values (both ways work)
print(f"Docker image: {config.optimizer_image}")              # Via convenience property
print(f"Docker image: {config.docker.optimizer_image}")       # Via nested access
print(f"Max build: {config.scheduler.default_max_build}")     # Direct section access

# Load heuristic plugin
plugin = load_plugin("fifo")

# Create and run scheduler
scheduler = Scheduler(
    demand_root="/path/to/families",
    plugin=plugin,
    max_build=config.default_max_build,
    max_solve=config.default_max_solve
)

# Discover and run jobs
jobs = scheduler.discover_jobs()
scheduler.run()
```

## Architecture

### Core Components

- **Job**: Represents a family optimization job with state management
- **Scheduler**: Orchestrates job discovery, selection, and execution
- **Runner**: Executes Docker containers for build/solve phases  
- **Monitor**: Extracts CPU/memory metrics from job logs
- **Store**: Records job events in JSONL format

### Plugin System

Aura supports pluggable heuristics for job selection:

- **FIFO**: First-in-first-out scheduling (included)
- **Custom**: Implement `HeuristicPluginProtocol` for custom logic

Example custom plugin:

```python
from aura.plugins import HeuristicPluginProtocol

class MyHeuristic:
    def name(self) -> str:
        return "my_heuristic"
    
    def select(self, candidates, running, capacity_total, cap_build, cap_solve):
        # Your selection logic here
        return selected_jobs[:capacity_total]
```

## Docker Requirements

Aura requires Docker to execute optimization containers. The optimizer image should:

1. Include `/optimizer/run_build.sh` and `/optimizer/run_solve.sh` scripts
2. Accept volume mounts for input files and output logs
3. Generate standard output files (result_cost.csv, etc.)

## Monitoring & Logging

### Event Logs

Job events are stored in `{runs_dir}/{job_id}.jsonl`:

```json
{"ts": "2025-01-10T14:30:00", "job_id": "abc-123", "family": "family1", "phase": "build", "kind": "started", "state_at_write": "BUILDING", "meta": {...}}
{"ts": "2025-01-10T14:30:45", "job_id": "abc-123", "family": "family1", "phase": "build", "kind": "finished", "state_at_write": "BUILT", "meta": {"ok": true, "duration_sec": 45.2}}
{"ts": "2025-01-10T14:35:20", "job_id": "abc-123", "family": "family1", "phase": "solve", "kind": "finished", "state_at_write": "SOLVED", "meta": {"ok": true, "duration_sec": 120.5, "model_cleanup": {"success": true, "file_size_mb": 387.2}}}
```

### Metrics

CPU and memory metrics are extracted from job-generated CSV files and included in event metadata.

## Model File Cleanup

Aura automatically deletes large `model.pb` files after successful solve completion to save disk space:

- **Automatic**: Enabled by default (`cleanup_model_after_solve: true`)
- **Space Savings**: Typically 300-400MB per job for 1-year demand files
- **Safe**: Only deletes after successful solve completion
- **Logged**: Cleanup results included in event logs with file size information
- **Configurable**: Can be disabled via configuration or environment variable

```bash
# Disable cleanup globally
export AURA_STORAGE__CLEANUP_MODEL_AFTER_SOLVE=false

# Or in config.yaml
storage:
  cleanup_model_after_solve: false
```

The cleanup process:
1. Runs automatically after successful solve completion
2. Records original file size before deletion
3. Logs success/failure with details
4. Updates event metadata with cleanup results
